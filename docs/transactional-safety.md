# Transactional safety (review-only)

Migrations 012 and 013 are **not applied to the established local or remote Supabase database**. The isolated test harness creates a random disposable database inside the verified `voicepilot-local-loopback` PostgreSQL container, installs the minimal fixture schema and both migrations, runs concurrency/permission checks, then drops only that database. Run `node scripts/test-transactional-safety.mjs` after confirming the Compose stack is healthy. The harness refuses unexpected volume, project, published ports or 001–011 ledger state.

## Design

- `provider_replay_claims` retains tenant/provider/event identity. `voicepilot_safety.claim_replay` uses a single conditional `INSERT ... ON CONFLICT DO UPDATE`, so simultaneous claims cannot both win. Expired keys may be reclaimed at expiry. `cleanup_replay`, `cleanup_action_reservations` and `cleanup_rate_windows` delete bounded eligible batches with `SKIP LOCKED`; retention scheduling and observability are not deployed.
- `reserve_action` serializes a tenant/provider queue using transaction-scoped advisory locks, checks explicit global and organization stop rows, marks expired reservations, then checks the stored `provider_limits` capacity and inserts. Exact idempotent retries return the original active reservation; released/expired keys remain tombstones until retention cleanup. A conflicting key fails. `claim_rate` uses an atomic minute-bucket UPSERT against a stored per-tenant/provider rate limit. These are offline database contracts, not a production scheduler.
- The global stop is a singleton in `voicepilot_safety.provider_global_stop`; organization stop rows remain in `public.provider_safety_controls`. Missing rows fail closed. Global updates require a pre-provisioned enabled operator; organization stop, limit and budget updates require an owner/admin membership. Every control mutation binds its actor argument to `request.jwt.claim.sub`; missing or mismatched identity fails closed. Shared/exclusive transaction advisory locks serialize safety-checked operations with global and organization stop changes. Only `service_role` has routine execution grants. Application callers must additionally authenticate and authorize the selected organization before using any privileged connection.
- `provider_usage_accounts` row locks serialize budget checks. Direct usage events are idempotent; conflicting keys fail. Usage reservations hold budget, settlement records an amount no greater than the reservation, and expired reservations release held budget. Values are bounded to JavaScript safe integer cents, with numeric comparison before adding. Audit entries are written transactionally to `voicepilot_safety.provider_safety_audit`.
- No client or public role has table access or privileged function execution. RLS is enabled, the private schema is not PostgREST-exposed, SECURITY DEFINER functions use `search_path=pg_catalog`, and all objects are schema-qualified. The service role receives SELECT only on the two control tables read by `PostgresDurableSafetyStore`; state mutation remains behind restricted routines. The adapter accepts only an injected, server-side parameterized SQL executor and fails closed on missing rows or unavailable database state. No provider/outbound path invokes it.

## Limits before any production rollout

The SQL routines are not a complete calling-safety system. A future active operation must freshly authorize tenant, consent, opt-out, calling hours, global/organization stop, limits and provider policy immediately before execution. The service role is powerful; possession of that credential can set PostgreSQL request-context settings, so production requires a narrow trusted gateway that derives actor and organization from a verified session rather than client input. The server caller must not accept a client-provided organization ID without independent membership verification. Provider-specific signatures, durable cleanup scheduling, operator provisioning, audit immutability/retention, monitoring, failure drills and reconciliation remain separate work. The in-memory stores are tests only. The generic HMAC contract does not verify Twilio, Telnyx or LiveKit signatures.

## Rollback plan (approval required)

Before any deployment, inventory dependencies and archive synthetic safety/audit rows if retention requires it. Disable future callers first. In a maintenance transaction, revoke service-role execution, remove only the `voicepilot_safety` routines/tables/schema introduced by 013, then remove 013-added columns from 012 tables **only if no data depends on them**. Migration 012 tables can be removed separately in reverse dependency order after verifying no callers or records require them. Never roll back by resetting the established database; rehearse against a disposable copy and require a separate approval for any real database change.
